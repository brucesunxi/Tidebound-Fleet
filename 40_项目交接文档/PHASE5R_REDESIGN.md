## 3. 精确定义玩法

### 3.1 固定方向与全程判定

`position` 是船尾格，方向向量为整数四方向。船体占格为 `position + k × direction`，其中 `k = 0…length-1`，width 固定为 1。

从船头前一格扫描到该方向的棋盘边界；任何其他船的占格都属于阻挡，不能只检查相邻格或第一个空格。出边还必须属于允许的出口范围。本阶段四条边全部允许直出。

- **畅通：**播放直线离场动画，船尾完全离开后一次性释放占格，发出一次 `ShipExitBoardEvent`，进入外围航道。
- **受阻且前方有空格：**沿方向移动空格数对应的距离，使船头停在最近阻挡格之前；到达后原子提交新位置与占格，再播放反馈，不退回起点。
- **紧邻阻挡：**位移为0，仅播放轻反馈；不改变位置或占格。方向始终不变。
- 设船头前连续空格数为 `d`，受阻时 `newTail = oldTail + d × direction`；动画结束前保留旧占格并持有操作锁，提交后重建依赖。
- **忙碌／暂停：**沿用现有操作锁与暂停契约。动画结束前占格不提前释放。
- **空格：**不选择船，不自动吸附邻船。

四边出场口与顶部中央舰队入口是不同概念。朝下、朝左、朝右的船先从对应边离开，再由外围航道汇合到顶部；顶部中央入口不是所有船必须在棋盘内直达的单一缺口。

### 3.2 完整阻挡图

约定 `A → B` 表示 **在当前几何状态下，B 占据 A 的完整离场路径**。B 必须移开该路径，A 才能完整离场；B不一定必须先离场，部分移动也可能解除阻挡。

每船记录整条前向路径上的 `blockerIds`，并另外记录最近阻挡、连续空格数和本次落点。完整集合用于结构分析，最近阻挡决定本次真实移动距离。

任何部分前进或离场提交后，都要重新计算依赖；旧图不能继续作为当前图使用。部分前进可能解除旧阻挡，也可能占据其他船的出口路径。

- 当前完整图无环，可以证明存在一条只点击直出船的清盘序列。
- 当前图有环，不足以单独判定死局；必须考虑部分前进后的状态。
- 没有直出船但仍有船能前进，不等于死局。
- 无船能前进也无船能离场，是终端卡死状态；更一般的无解结论需要完备搜索或严格的硬锁证明。
- “初始有完整解”不等于“玩家任意合法点击后都仍有解”。撤回上一版只增删依赖、任意顺序安全的结论。

### 3.3 “最优解”的边界

以每次改变局面的点击（部分前进或完整离场）计1步。紧邻阻挡的零位移操作不进入搜索；实际操作统计仍可记录它。

N 艘船的解至少需要 N 次离场。反向插入生成器保留一条每步直接离场的 N 步序列，因此该类样本初始状态的最优步数可证明为 N。

玩家提前推进受阻船后，原序列可能失效；其他布局也可能需要额外的中间位移。Solver必须从当前状态重新求解，不能把所有完整序列都写成N步。证明回放记录每一步的船ID、起点、终点、结果和前后状态指纹，同一船ID允许多次出现，但离场只能一次。

找到完整序列只证明 `Solved`；只有达到 N 步下界或完备最短路搜索时才能标记 `optimality=Proven`。预算内找到解但未证明最优时返回 `optimality=Unproven`；预算耗尽且无已知解时返回 `LimitReached`，不得误报死局。

## 4. 反向生成算法

### 4.1 先设出口和结构目标

初始化空 Grid、四边开放的 `exit` 定义、目标船数、长船数量、初始可出数量区间、最长依赖链区间与解锁节奏模板。先规定哪些边用于首批离场，不将某一片区域固定为某个方向。

结构模板由短链、交叉链、多个独立起点、共享阻挡点构成。“共享阻挡点”指移走同一艘船同时满足多艘船的一项依赖，并不保证它们立即都能出场。

这些是几何约束下的目标，不是假设任意 DAG 都可以嵌入网格。无法几何实现的结构必须回溯或报告失败。

### 4.2 从最后离场的船向前构造

首次放入的船代表正向解题时较晚离场的船。每次加入新船 C，必须满足：

1. C 的船体完全在 Grid 内且与已有船无重叠。
2. **C 自己到出口的整条路径，在当前构造状态下完全畅通。**
3. C 的占格可以落在已有船的出口路径上，形成 `已有船 → C`。
4. 除设计指定的独立链种子外，新船应至少新增一项真实阻挡关系。
5. 插入后的完整依赖、空间分布和目标约束仍有可能完成；否则撤回该次插入。

不能“随便把阻挡船放进去再看 Solver 能否救回来”。如果 C 自己被已有船挡住，就不满足本反向构造的不变量。

```text
Generate(profile, seed, budget):
    define all four edge exits
    board = empty
    insertionOrder = []
    while shipCount < targetCount:
        enumerate non-overlapping candidates with their own exit path clear
        derive new dependency edges from candidate geometry
        rank by remaining structure targets, then spatial coverage
        choose a legal candidate deterministically from seed
        if no candidate or remaining targets become infeasible:
            backtrack within budget; otherwise return GenerationFailed
        commit candidate and append id to insertionOrder

    constructionWitness = reverse(insertionOrder)
    solved = LevelSolver.Solve(from freshly serialized level)
    replay constructionWitness and solved.solutionOrder through runtime rules
    evaluate structure gates and portrait layout
    return only when all hard gates pass
```

随机种子仅打破合法候选之间的并列，不先随机填满再给船找方向。候选不足不能偷偷改船长、旋转已放船、降低船数或退回旧铺排算法；返回失败原因、已放数量和触发的预算。

### 4.3 为什么能保证可解

设插入顺序为 `S1, S2, …, Sn`。插入 `Sk` 时，它的出口路径没有 `S1…S(k-1)`。最终从 `Sn` 开始反序移除：移除所有更晚插入的船后，`Sk` 所处的阻挡状态恢复为插入时的状态，所以它一定能驶出。数学归纳得到完整清盘序列。

反向序列只点击当时可直出的船，所以在允许受阻部分前进的规则下仍然成立。它证明初始状态存在完整解，不保证所有玩家操作分支安全。

保证的是 **生成成功并通过校验的关卡初始状态可解**，不是保证每个 seed、每种密度和每组结构参数都能在有限预算内生成成功。

### 4.4 防止“反向生成但仍不好玩”

本批反向直出样本的硬门槛：无重叠越界、全路径合法、初始依赖无环、船数正确、无道具完整清盘、证明与内容绑定、出口与界面匹配。

结构目标：

- 初始可出船数量及比例，设置上限和下限。
- 依赖最长链：以船节点数计，零阻挡船深度为 1。
- 每步可出船数 `available[k]` 和本步新解锁数量 `unlocked[k]`。
- 前 60% 解题过程的可选数量分布，防止“开局略堵、很快整盘全自由”。末段允许自然放宽。
- 共享阻挡点、独立链数量与空间分散程度。
- 前向路径长度、跨行列交错情况；方向比例只作辅助指标。
- 空间覆盖、中心大空洞、方向条带、局部拥挤和同构重复。

除记录标准 Solver 序列外，还用固定种子的多种合法选船策略回放并比较节奏。策略样本不是所有操作分支的穷举。初始可解性由反向序列和真实回放证明；另加入提前推进受阻船的偏离操作样本，检查动态依赖和可能的死局，并记录覆盖范围。禁止把抽样未发现死局写成所有可达状态均安全；此类更强保证需完整状态验证或另给严格证明。

优先级：规则正确 > 可解证明 > 结构节奏 > 触控可读 > 数量密度 > 视觉装饰。结构指标不等于真人难度，只是筛选条件。

## 5. 数据与代码职责

### 5.1 概念数据契约与增量实现

2026-09-19路线优化：以下是概念视图，**不直接新增 v3 布局**。首轮保留现有 schema v2；grid 映射 width／height，shipType 映射 typeId，rotation／width／exit 由固定规则推导；规则、生成参数、solutionSteps 与指标放在版本化伴随证明文件中，字段及验收见 [后续计划第5节](PHASE5_PLUS_PLAN.md#5-保留布局契约增量完善证明)。这样保留用户要求的数据语义，并减少加载与编辑链路迁移。

```text
Ship {
    id,
    position: { x, y },      // 船尾、整数 Grid
    direction,              // Up / Right / Down / Left，逻辑唯一来源
    rotation,               // 表现角度校验值，由 direction 推导
    length: 2 | 3,
    width: 1,
    shipType: TF_BASE_SHIP
}

Level {
    schemaVersion: 2,          // 实际布局保留现有v2，以下为聚合概念视图
    rulesVersion: ForwardUntilBlockedV1,
    levelId,
    grid: { columns, rows },
    ships: Ship[],
    exit: { mode: AllBoundaryEdges, sides: [Up, Right, Down, Left] },
    solutionOrder: shipId[],     // 通用解允许同一船多次出现
    solutionSteps: { shipId, from, to, outcome, beforeHash, afterHash }[],
    generation: { algorithmVersion, seed, profileId },
    proof: { contentHash, solverVersion },
    metrics: { initialExitCount, dependencyDepth, availableByStep, ... }
}
```

`rotation` 必须与方向一致，禁止成为第二套逻辑方向。以船素材局部船头朝上、角度顺时针计：Up=0°、Right=90°、Down=180°、Left=270°，Unity 适配层转换到自身旋转约定。width 现阶段只接受 1，不假装支持多格宽船。

`shipType` 映射现有逻辑 `typeId`，不能恢复多船型能力；skinId 仍不写入关卡静态布局。`grid` 保存尺寸，占格表从 ships 唯一重建，不能维护两份权威布局。

`solutionOrder` 是可复算证明，不是限制玩家点击的脚本。`proof.contentHash` 对规范化的 rulesVersion、grid、exit、ships 和逻辑字段计算；不包含 hash 自身、解法和可重算指标，避免循环定义。布局、朝向、出口或规则版本改变均使旧证明失效。

旧 schema v2 资产保留为历史夹具；布局兼容不等于证明有效，必须按当前规则重建指纹、显式升级证明并完整回放后才能成为新候选。未来出现不兼容布局字段时再单独设计迁移工具。

### 5.3 LevelSolver 的行为

1. 校验几何、字段、出口和规则版本，非法输入返回 `Invalid`。
2. 从当前占格重建完整前向阻挡集合与实际路径查询，不信任生成器提供的图或旧 solutionOrder。
3. 快路径：尝试仅直出船的剥离序列；若真实回放以N步清空，返回 `Solved` 和 `optimality=Proven`。
4. 快路径无法清空时，从原始当前状态进行有界状态搜索；枚举每艘船的真实动作，既包括离场，也包括到最近阻挡前的非零位移。不能把快路径残余环直接判为无解。
5. 以船ID及其当前位置、方向、长度、存活状态等构造规范状态键，去重并保存父状态／动作。使用等代价BFS时，首个完整解即为最短解；其他搜索策略若无最优性证明必须明确标记。
6. 每个搜索后继都通过与运行时相同的 `QueryForwardPath`／`ApplyPathResult` 执行，并更新依赖。零位移不扩展搜索。
7. 完备搜索无解返回 `Deadlocked`；严格硬锁证据也可提前返回。无直出或一般环本身不是充分证据。预算耗尽返回 `LimitReached`，若已持有有效解则返回该解并注明最优性是否已证。

图分析约为 `O(N × max(columns, rows) + E)`；纯直出剥离阶段可为 `O(N+E)`，但不能把这个复杂度用于包含部分位移的通用求解器。80船状态搜索必须设置状态数、时间与内存预算，并如实记录求解覆盖和未知状态。

| Level 4 | 80 | 4 | 10～14 | 7～10 | 长船占格与完整路径判定 |
| Level 5 | 80 | 4 | 8～12 | 8～12 | 一个阻挡点服务多个依赖，形成释放反馈 |
| Level 6 | 80 | 4 | 12～16 | 6～9 | 节奏放松，验证不靠单调增加难度 |
| Level 7 | 80 | 6 | 8～12 | 10～14 | 多个交叉子结构，跨区域观察 |
| Level 8 | 80 | 6 | 6～10 | 11～15 | 前向路径有多个阻挡，拒绝只看最近一个 |
| Level 9 | 80 | 6 | 6～10 | 12～16 | 深链与共享阻挡组合，避免全盘长时间只剩一个候选 |
| Level 10 | 80 | 8 | 6～10 | 12～18 | 综合结构，验证同一规则与同一屏幕空间 |

Level 1 使用与其他关相同的场地边界和单格尺度，把 7 艘集中布置在中部约 6×8 的教学构图区；该构图区不是额外墙体或新的出口边界。保留引导高亮，避免先用巨大船教学、第二关再突然缩小。

每关交付 JSON、规则／布局 hash、确定性 seed、Solver 序列、真实回放记录和结构指标。这批反向直出样本的基准解长度必须等于船数；偏离后重求解允许增加部分移动步数和重复船ID。每个 ID 正好离场一次，最后 Grid 为空、无重叠、无道具、无转向、无偷偷重排。

## 7. 统一竖屏边界

### 7.1 参考图取舍

- 挪猪图用于理解“密集但方向可读、上下功能区与中间对象区分开”，不照抄对象和配色。
- 舰队图用于确认顶部战区、中部船阵、底部道具的分工；图中船数、船身比例、空隙和出口不作为逻辑依据。
- 不先用美术图塞满屏幕再反推 Grid，也不把 Boss 特效伸进船头识别区域。

### 7.2 布局公式

坐标全部以扣除系统安全区后的 `S=(W,H)` 项目逻辑单位计算，以下是首轮灰盒候选，不能等同于实测 dp 或毫米。

```text
topHeight   = clamp(0.22 × H, 128, 196)
toolsHeight = clamp(0.14 × H, 88, 120)
gap         = 8                        // 上中、下中各一个
middleHeight = H - topHeight - toolsHeight - 2 × gap
sidePadding  = 8
laneThickness = 12
cell = min((W - 2×sidePadding - 2×laneThickness) / columns,
           (middleHeight - 2×laneThickness) / rows)
```

上区贴安全区顶部；下区贴安全区底部；中区位于两者间。Grid＋航道在中区水平、垂直居中，余量作为水面呼吸空间，不能通过拉伸单格消掉。明确输出各 Rect 和 Grid 原点，渲染、触控、航道使用同一份布局结果。

优先灰盒候选 **14×18**：80 艘占 160～168 格，占用率约 63.5%～66.7%。比较候选为 14×16 和 14×20，仅用于评估触控、结构与空间效率。它们全部待验证；旧 12×18 不自动恢复为正式规格，18～22 列也不再默认正确。

选择较少列数是为了扩大短轴触控宽度；不承诺该选择一定满足 80 艘的依赖结构和触控。14×16 更密，14×20 在矮屏上单格更小，必须用同一套验收比较。

| 安全区 | 顶部 | 底部 | 中部 | 14×18 单格 | 棋盘净尺寸 |
|---|---:|---:|---:|---:|---:|
| 360×640 | 140.8 | 89.6 | 393.6 | 20.53 | 287.47×369.60 |
| 390×844 | 185.68 | 118.16 | 524.16 | 25.00 | 350.00×450.00 |
| 430×932 | 196.0 | 120.0 | 600.0 | 27.86 | 390.00×501.43 |

表中为公式计算结果，不是设备测试结果。尤其 360×640 上约 20.5 的船体短轴仍有明显触控验证风险，不能称为已达标。若失败，应重新评估网格、顶部最小空间和支持的最小安全区；不能扩大点击热区去重叠邻船，也不能私自缩减约 80 艘目标。

### 7.3 各区域的职责

| 区域 | 内容与边界 |
|---|---|
| 顶部 HUD | 关卡号、暂停和金币；暂停目标至少 48×48，紧凑版可与其他信息分列 |
| 顶部战区 | Boss、血条、舰队接入预留；灰盒只画占位，不创建攻击和扣血逻辑 |
| 中部航道 | 环绕 Grid 的独立非点击区域；四边均可接入，上方汇合，不占逻辑格 |
| 中部船阵 | 所有关共用 Grid 尺度与定位方法；不用每关独立适配或随机偏移整盘 |
| 底部道具 | 三个等宽入口，最小目标 48×48、间隔至少 8；灰盒禁用且明确预留 |

不通过放大 Boss 挤压棋盘；不让道具覆盖最下排船；不让航道动画占用船的点击映射；不按手机宽高比改变同一关的逻辑坐标、船数、方向或解法。

船的视觉体收在逻辑 footprint 内，头部统一方向标、尾部清晰，关闭网格线仍能识别。贴图边距不是逻辑空格，轻微模型留白不允许船从视觉缝隙穿过。

同一关在不同手机上只做整体等比缩放与平移；不滚动、不捏合缩放、不拉长船体。Level 1 留白多属于教学设计，不单独放大其船体。

## 8. 验证和停止条件

### 8.1 规则与求解测试

- 相邻阻挡为零位移；隔1／3格阻挡分别前进1／3格，停稳后提交新位置与占格，不回弹。
- 四方向、1×2／1×3 船均检查直到边界；尾部未离界不能释放。
- 前方两个或更多阻挡全部入图，移走最近一个后仍受后方阻挡。
- 两船对向硬锁必须识别；一般依赖环先分析部分位移，覆盖有环可解与有环无解的手工反例。
- 无环图可用直出证明；混合“部分可清＋残余环”进入真实状态搜索，重复ID／越界／重叠为Invalid。
- 正确处理空棋盘、边界船、非法方向、未知规则版本和过期证明。
- 不同 seed 生成的成功样本均按反向序列和独立 Solver 序列验证；不能只验证生成器自己保存的序列。
- 至少使用确定性 ID、最大即时解锁、最少即时解锁和固定种子选择等策略回放。并加入提前部分前进策略；统计已解、死局和预算未知。抽样结果不证明所有操作分支安全。
- 生成预算耗尽返回失败，不能保存不合格产品关。

### 8.2 10 关及 Unity 集成验收

- 新规则下 10/10 个固定数据完整清空；Level 1=7 步、Level 2～10 各 80 步。
- Unity PlayMode 从真实 JSON 加载，以真实移动完成回调推进；最终逻辑船数与视图船数一致，出场和航道入舰事件各船恰好一次。
- 受阻反馈、暂停、重置、Busy、旧操作回调等不破坏占格、不重复离场。
- 保留现有受阻前进回归断言，新增动态依赖、连续点击已停船、重复ID步骤和偏离基准序列测试；不删除失败用例以维持虚假的全绿。

### 8.3 竖屏与真人验收

- 三类安全区全部验证上中下不重叠、四边航道可見、全部占格可点击、坐标正反映射一致。
- 5 名首次玩家各 30 次指定点击，目标命中率 ≥95%，方向识别 ≥90%；记录设备与失败位置。
- 第 2 关目标至少 4/5 玩家在 3 秒内发现一个可出目标；若失败先诊断方向、候选分布和视觉尺度。
- 验证玩家理解“先前进到阻挡前，停在新位置；阻挡移开后可再次前进或离场”。
- 最低目标 Android 设备持续操作 ≥30 FPS，记录峰值内存和动画／航道并发；未明确或未拿到设备不能标记通过。

### 8.4 实施顺序

1. 按用户确认保留受阻前进规则，统一文档、求解器与数据证明，补充动态回放测试。
2. 完整依赖图与 `LevelSolver.cs`，先做手工正反例。
3. `ReverseLevelGenerator.cs`、结构约束、预算失败与确定性输出。
4. 固定 10 关并在真实运行时自动通关，保存新验证记录。
5. 同一数据接入三段灰盒，完成真人／真机验证，冻结网格与摆放边界。
6. 在上述验收之后接入海怪战斗；每船一次攻击事件仍独立于关卡几何和求解。
