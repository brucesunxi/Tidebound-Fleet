# Tidebound Fleet 关卡编辑器与验证工具规划

版本：3.0
日期：2026-09-19
状态：旧原型工具保留；I1算法与两个样关导出入口已实现，I2／6A完整工具接线待实施，6B量产工具后移。当前顺序以[后续计划](PHASE5_PLUS_PLAN.md)为准。

## 1. 工具定位

Tidebound Level Studio 是原创关卡的生产和验证工具。它不负责把棋盘随机塞满，而是帮助策划构造、观察、求解和筛选阻挡依赖网络。

工具只存在于 `Tidebound.Editor` 程序集，直接读写运行时使用的 JSON，并复用 BoardModel、BoardValidator 和真实移动事务。Scene、Prefab 和 ScriptableObject 不保存第二份布局。

## 2. 源码调研结论

- Cocos 正向源码有方向笔刷编辑器，能制作18×22／112对象和18×18／92对象的密集矩阵，但只输出控制台文本，没有求解或难度分析。
- Cocos 逆向源码保存89个手工坐标模板，教程7个对象，第二模板101个，第三模板109个；正式关卡不是运行时随机生成。
- Unity Bus Mania 使用101个独立Scene手工摆放，没有数据型编辑器。

因此采用“Cocos方向笔刷＋Unity EditorWindow＋Tidebound真实规则＋求解与依赖分析”的专用方案。详细证据见 [LEVEL_SOURCE_AUDIT.md](LEVEL_SOURCE_AUDIT.md)。

## 3. 编辑模型

### 3.1 基础编辑

- 重构候选14×18，比较14×16、14×20；历史18～22列样本保留回归，4×6教学夹具不代表最终屏幕区域。
- 左键放置，右键删除，拖动选择。
- 方向笔刷：上、下、左、右。
- 长度笔刷：2、3。
- 船尾、船头、完整占格和方向箭头使用不同标记。
- 允许移动、旋转、改长度、复制、框选和批量删除。
- 支持 Undo／Redo、水平镜像、垂直镜像和180°旋转。
- 允许锁定关键船，避免批量变体破坏核心结构。

### 3.2 结构视图

编辑器提供三种可切换视图：

1. **棋盘视图：**显示实际占格、方向和空白。
2. **依赖图视图：**以船为节点，显示当前首个阻挡对象和依赖边。
3. **热力图视图：**显示出口、拥堵、强制步骤、局部密度和点击频率。

依赖边必须来自真实路径查询，不能通过几何距离猜测。

## 4. 数据与保存

- JSON 是唯一布局源，保存 schemaVersion、levelId、width、height、bossId 和 ships。
- ship 保存稳定 id、typeId、position、direction、length；皮肤不写入关卡。
- Open／Save／Save As／Duplicate 使用原子写入。
- 自动维护关卡清单和设计备注，备注不进入运行时 JSON 时可放伴随 `.design.json`。
- 每次保存写入结构摘要哈希，变更后旧解法证明自动失效。
- 非法关卡只能保存为草稿，不能标记为 Candidate 或 Approved。

## 5. 四层验证

### 5.1 数据合法性

- schema、ID、方向和长度合法。
- 完整 footprint 在界内且不重叠。
- 船型和 Boss 引用存在。
- 视觉资源缺失只提示，不改变逻辑判断。

### 5.2 解法证明

策划可在工具内按真实规则试玩并录制操作序列。保存候选时从初始 JSON 重新加载并完整回放：

- 每一步都必须是当前状态的合法事务。
- 被阻挡移动必须提交新的船尾位置。
- 出界必须完整释放占格。
- 最终棋盘为空。

成功回放可以严格证明“至少存在一条无道具解法”。它不等于证明所有选择都安全。

### 5.3 搜索与死局分析

使用分层方案，避免对100艘状态空间做不现实的穷举承诺：

- 小关和裁剪子图使用完整状态搜索与状态哈希。
- 大关先尝试直接离场剥离，再结合真实移动分析；有环或没有直接出口都不能单独判死局，受阻船可能仍能前进并改变依赖。只有严格证据才能报告死局，预算耗尽必须返回未知。
- 对完整关执行有界搜索、启发式多路线和随机策略采样，统计可达死局率。
- 候选生成时保存一条构造解，确保至少可清盘。
- 所有搜索都调用同一状态转换器，不复制移动规则。

### 5.4 真人体验

工具验证不能替代体验。Candidate 还必须经过方向识别、触控、首步发现时间、过程分支和完成时长测试，才能变为 Approved。

## 6. 难度指标

每关至少输出：

| 指标 | 含义 |
|---|---|
| ShipCount | 总船数 |
| Occupancy | 占用率 |
| DirectionEntropy | 四方向混合程度 |
| DirectionClustering | 同方向空间聚集度 |
| InitialExitCount | 开局可直接出场数量 |
| InitialMoveCount | 开局能前进但未出场数量 |
| MeanBranching | 解法路径平均可选数 |
| ForcedMoveRatio | 只有一个合理选择的步骤比例 |
| DependencyDepth | 最长阻挡链 |
| CycleCount | 依赖图中的环数量 |
| CriticalShips | 移除后大量解锁的关键船数 |
| SampledDeadEndRate | 多策略采样进入死局的比例 |
| SolutionLength | 证明序列的总点击数 |
| PartialMoveCount | 解法中受阻移动次数 |
| Similarity | 与已批准关卡的结构相似度 |

方向数量平均并不代表布局合格；`DirectionClustering` 必须阻止四个方向被分成四块区域。

## 7. 候选生成

自动化只生成候选：

1. 选择目标网格、船数、长船比例和难度区间。
2. 构造一条合法清盘序列或从已批准依赖骨架变体开始。
3. 反向放置时同时约束方向混合、空间聚集、出口分布和依赖深度。
4. 正向重新回放，确认构造解仍成立。
5. 运行死局分析、相似度和视觉规则检查。
6. 进入人工调整与试玩。

禁止把纯随机多米诺铺满、规则条带或仅镜像现有关卡直接发布。

可接受的批量变体包括：

- 保留依赖骨架，改变局部空间嵌入。
- 锁定关键船，对非关键子图重新排布。
- 镜像或旋转后，再进行局部重构并重新评分。
- 在不改变逻辑长度的情况下随机分配皮肤预览。
- 调整少量方向和空白位置，重新求解。

## 8. 工作流状态

```text
Draft
  ↓ 数据合法
Candidate
  ↓ 解法证明＋指标范围＋人工试玩
Approved
  ↓ 进入版本关卡清单
Published
```

任意布局、规则或 schema 变化都会使 Candidate／Approved 的解法证明和难度报告失效，必须重新验证。
