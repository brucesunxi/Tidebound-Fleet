## 评估结论

**建议继续采用购买的 Unity 工程作为基础，在后续获准开发时分阶段替换玩法核心；Cocos 正向用于借鉴棋盘规则，Cocos 逆向用于研究关卡与商业交互。三个工程目前均不能标记为“已验证正常运行”或“可以直接上架”。**

| 项目 | 完整性判断 | 运行判断 | 推荐定位 |
|---|---|---|---|
| Unity Bus Mania | 标准工程骨架、主体脚本、关卡和资源齐备；存在明确依赖缺口、移动端编译问题及待核实引用 | **未实机／编辑器运行；原样交付不能按可正常构建验收** | 最终工程基础、3D 表现与通用 UI 的候选资产库 |
| Cocos 正向救救小猪 | 可编辑的 Creator 源工程；1 场景、40 个业务 TS、11 个 Prefab、4 关；部分资源引用需编辑器核实 | **具备尝试本地预览的基础；存在确定的棋盘逻辑缺陷，不能认定玩法正确** | 最清晰的四方向占格／受阻停留参考 |
| Cocos 逆向猪了个猪 | 恢复为 Creator 工程结构；业务 JS、场景、89 份关卡和大量界面资源保留；不是原始 TS 工程 | **51 个 JS 通过语法检查；本地预览、资源反序列化和商业服务仍未验证** | 密集棋盘、关卡排序、连击、图鉴、道具及商业流程参考 |

“完整”分为工程结构完整、资源依赖闭合、功能正确、构建通过、线上服务可用五层，不能相互替代。购买目录名称中的“100”“BugFix”“逆向”不作为质量证明。

#### 核心脚本与系统关系

| 模块 | 关键脚本 | 已有行为 |
|---|---|---|
| 启动 | SupersonicManager、LevelManager | Wisdom 初始化完成后加载地图或关卡 |
| 车辆 | Vehicle、VehicleController、Garage | 点击、前方检测、碰撞、出场、转弯、车库逐辆释放 |
| 停车与乘客 | ParkingManager、ParkingSlots、PlayerManager、Player | 预占停车位、按颜色上客、坐满离场 |
| 胜负 | GameManager | 车辆全部装满离开计胜；停车位满且乘客颜色不能匹配触发失败 |
| UI | UIManager、Helper、LevelMapInstantiator、GiftBox | 胜负面板、重试、下一关、引导手势、地图和礼盒 |
| 商业 | ISManager、PowerUps、CoinsManager | 广告复活、解锁车位、排序、洗色、直升机、金币 |
| 通用表现 | SoundController、EffectsManager、Vibration、EventManager | 声音、特效、震动、部分事件分发 |

**关卡系统：**主体采用“一个关卡一个场景＋场景摆放的 Prefab”，不是配置驱动的逻辑棋盘。进度保存到 PlayerPrefs，用 Build Index 加载；超过阈值后从索引 20 起选择未重复的随机场景，并保存已选索引。UI 的关卡号、插入的 `.1` 教学场景和 Build Index 之间需要做完整映射检查，尤其是末关回流；不能把目录中的 100 关原样视为船棋盘的 100 关。[LevelManager][U06]

**移动系统：**`Vehicle.OnMouseDown` 检查全局移动锁、当前对象状态、UI、车库及道具；以 `transform.forward` 和 Physics.Raycast 找前方车辆。没有障碍时先申请停车位，再 Tween 直行，边界 Trigger 触发转向，沿路进入车位。方向来自 Transform 朝向，而不是受约束的四方向枚举。[Vehicle 点击与检测][U07]

有障碍时会向前运动并触发碰撞反馈，随后 **Tween 回到 originalPosition**。用户要求是“驶到阻挡位置、撞击、在新位置停住”，因此只能借鉴动画感受、边缘转弯和路径表示；**占位判定、停船结果、出场条件和状态更新必须重建**。[碰撞分支][U08]

当前移动还依赖单条射线、Collider、静态 `isMovingStraight` 以及多个 Singleton；不同船长、快速连点和多船并行下的可靠性没有得到验证。不应由物理接触回调决定逻辑棋盘的最终状态。

**UI 系统：**UGUI＋TMP，Inspector 绑定按钮，直接访问 GameManager、ISManager 等实例。通关下一步播金币粒子并加 50；默认金币设置为 **10000**。有界面素材与常用交互基础，没有所需的上部海战、舰队聚合、船只升级或 20／60／20 布局。[UIManager][U09] [CoinsManager][U10]

**广告系统：**`ISManager` 包含初始化、激励、插屏、底部 Banner、网络判断和间隔、暂停恢复及奖励分发。广告入口覆盖车位、乘客排序、车辆洗色、直升机、三倍金币和复活；广告奖励直接调用业务对象。`ParkingSlot` 分支把 `UnlockSlot_Callback()` 连续调用了两次，需要查清是否误发两次，不能作为安全的奖励发放模板。[广告奖励分发][U11]

**实际运行／构建障碍：**

1. URP 依赖缺口需补齐后才能验证渲染。
2. `Helper.cs:4` 在普通运行时目录无条件 `using UnityEditor;`，没有 Editor 宏或独立 Editor 程序集隔离，属于移动端编译阻断项。[Helper][U12]
3. `SupersonicWisdom.asmdef` 面向所有平台，却引用 `GameAnalyticsSDK.Editor`、`Unity.TextMeshPro.Editor`；至少前者本地明确限定 Editor，需要做 Player 程序集依赖整改／验证。[程序集定义][U13]
4. `SupersonicManager` 仅在 SDK Ready 回调中进入关卡，没有在该业务脚本中提供超时／离线进入回退。SDK 是否自行兜底本次没有运行验证，因此存在启动停滞风险。[启动链路][U14]
5. Android 配置有 IL2CPP、ARMv7＋ARM64、min SDK 23、target SDK 自动，以及自定义 Gradle／Manifest。iOS 标识仍为模板值，Android 标识属于原项目；这只是旧工程设置，不能证明已适配本项目的任何商店。

**数据与进度：**`LevelConfig.ts` 硬编码 `levelID`、`levelTime`、`pathList`；0 是空位，1／2／3／4 对应上／下／左／右。不是单格棋子：每个非零项代表一个对象锚点，并在前方相邻格写入同一对象引用，形成两格占位。[关卡配置][C02]

| 关卡 | 矩阵（行×列） | 对象数 | 限时 |
|---|---:|---:|---:|
| 1 | 5×5 | 5 | 120 秒 |
| 2 | 22×18 | 112 | 120 秒 |
| 3 | 3×5 | 5 | 120 秒 |
| 4 | 18×18 | 92 | 120 秒 |

本次按源码的两格规则检查这 4 份初始布局，没有发现初始占位越界或重叠；**没有据此证明所有关卡可解或难度合理**。第 2 关直接达到 112 个对象、第 3 关回落到 5 个，也不能按成熟的新手难度曲线照搬。末关结算有“已是最后一关”保护，并非必然跳入不存在的第 5 关。

`GameCtrl`、`GameData` 管理本地关卡／道具／状态；关卡编辑器允许摆方向和占格，输出矩阵到控制台，提示人工复制进配置表，缺少自动保存、验证和求解生产链。[编辑器导出][C03]

**移动逻辑：**`GameMainItem` 点击发送 `PigMove`，`GameMain.checkMove` 按方向扫描前方占位；有间隔才向最近阻挡前的可停位置移动，无障碍则驶出边界、缩小消失并检查棋盘清空。逻辑矩阵和 Tween 都集中在 GameMain，棋盘父节点旋转 45°。[移动实现][C04]

这是三个参考中最直接对应“受阻后留在新位置”的实现，但有明确缺陷：**紧邻障碍时，代码清空自己的原占格，`emptyPos` 仍为空，于是既没有移动，也没有把原占格写回。** 画面上的猪还在，逻辑矩阵却认为位置空了。四个方向都采用相同结构，可能引起穿过对象或错误清盘判定。

另外，路径距离计算使用 `this.node` 的位置而非移动对象当前位置；动画前更新占格、缺少明确的每船事务锁／路径预约，也需要在重新实现时处理。当前“撞击／晕眩”部分只是注释或空分支，不能认为完整碰撞反馈已经具备。

**平台与资源限制：**SdkCtrl 默认 `Platform.h5`，非小游戏分支直接调用广告成功回调；网页中拿到道具不等于真实激励视频成功。代码含微信／快手适配、旧广告位和服务地址，但这些不能直接复用于原生 Android／iOS。[SDK 分支][C05]

8 个序列化 UUID 在项目内未定位，涉及默认材质、按钮状态图及 SpriteFrame；其中一些很像 Creator 自带资源，未用对应编辑器核实前列为“待解析”，不统一算作缺失。工程没有明显的业务脚本／启动场景断链，但功能正确性不通过。

### 对方向图的具体判断

- 图 1 适合作为**中后期内容密度与美术氛围参考**，图 2 适合作为**新手场景与少船教学参考**。两张图都清楚表达了“底部出船影响上部战斗”，有助于玩家理解因果。
- 视觉层可统一热带海岛、明亮海水、卡通舰船和夸张 Boss；静态海岛背景、活动船只、航道、Boss 与 UI 应拆开制作。海面高光、箭头光带、爆炸和炮弹需要避免遮住棋盘方向。
- 按文字规则落实**安全区域内战斗 20%、棋盘 60%、道具 20%**。概念图特别是图 2 的战斗与过渡景观占用明显更大，不直接按像素照搬。海岸装饰和入口过渡要计入所属区域，而不是额外挤占棋盘。
- 图 1 上方有外观相似的重复战船；正式规则应是**每种船型仅一个展示实体＋数量／待攻击次数提示**。多艘同型船可以依次走完入场动画，抵达后融入这个实体。
- 图 2 的“点击船只向左或向右移动”会被理解为双向可选，与“每艘船只有一个固定方向”冲突。建议教学语义是“点击船只，沿箭头方向驶出”；图内文字不作为新需求。
- 图 1 部分箭头／符号容易与船头混淆。每艘船只显示一个清晰方向，船头、方向标记和点击结果一致；船型用轮廓＋颜色识别，避免只靠颜色。
- “移除船只”究竟是直接删除还是送入战场，洗牌是否同时改变方向，翻转是否 180°，会改变解谜和伤害预算。图片只确认了入口，不自动决定效果。
- 两张图中的关卡号、HP、道具“3”等数字均作为示意，不能据此确定真实成长数值或初始赠送量。

## F. 推荐最终 Unity 架构方案

### F1. 工程与渲染路线

**沿用购买 Unity 工程的工程基础与经验证资产，建立独立的 Tidebound 业务目录和程序集，逐步替换旧业务。** 保留原始素材目录作为只读参照；后续在工作副本建立可复现基线，不把它一边当证据、一边直接改造。

建议先用项目声明版本恢复运行以区分交付缺陷和升级问题；生产所用 Unity LTS／补丁在核心原型、原生 SDK 和 Android／iOS 构建验证后锁定。本机安装 Unity 6 不构成必须立即升级的理由。

表现采用适合现有资产基础的 **2.5D：逻辑二维网格＋3D／分层精灵表现＋UGUI**。棋盘用清晰的俯视或轻倾斜相机；上方战斗可以用独立视区，背景用分层静态图，舰船／Boss／炮弹为活动实体。先比较移动端清晰度和成本，再决定 Boss 使用 3D 模型还是 2D 骨骼；概念图本身不足以锁定美术管线。

旧工程中可验证保留 DOTween、音效、震动、TMP、通用面板及特效工具。乘客、颜色上车、停车位容量、车库和旧 GameManager 不进入新规则核心。商业 SDK 通过接口选择渠道实现，不与棋盘直接引用。

### F2. 逻辑分层

```text
UI / 输入
    ↓ MoveShip 指令
GameSession（单局状态、暂停、流程编排）
    ├── BoardDomain（占格、方向、阻挡、移动结果）
    ├── LaneTransit（离场后航道与到达事件）
    ├── FleetRegistry（同型唯一实体与聚合数据）
    ├── CombatDomain（攻击令牌、伤害、Boss）
    ├── FusionSystem（连融时间窗与特效档位）
    └── Settlement（胜负与一次性奖励）
           ↓ 领域事件
Presentation（船移动、碰撞、炮弹、Boss、UI 动画）

跨局：Progression + Economy + VersionedSave
配置：Level / ShipType / Boss / Fusion / Economy
外部：IAdService / IAnalytics / IAudio / IHaptics / ISaveStore
编辑器：LevelEditor / Validators / Solver / ReplayTools
```

这是职责划分建议，不是要求引入复杂框架。领域层使用普通 C# 数据与函数，不依赖 MonoBehaviour、Collider 或 Tween；GameSession 负责组合，表现层消费结果。编辑器工具单独程序集，避免重现当前 runtime 引用 UnityEditor 的问题。

### F3. 数据模型与移动契约

**关卡配置：**稳定 levelId、网格尺寸／有效区域、船实例列表、障碍、出口／航道配置、Boss 参数引用、道具规则、随机种子和配置版本。船实例至少包含 instanceId、typeId、锚点、Direction、船体占格形状。方向仅允许上下左右；逻辑方向不由随意旋转的 Transform 推断。

**船型配置：**模型／Sprite／图标／音效引用、占格、等级伤害参数、攻击表现、可用特效档位。占格建议支持整数长度，原型可先统一尺寸；“船型不同”不自动意味着船体尺寸也必须不同。

**逻辑状态：**Idle → MovingOnBoard → Idle 或 Exiting → InLane → JoinedFleet。加入舰队后该出场实例完成使命，由舰队对应 typeId 的展示实体承接反馈。

移动过程应明确：

1. 校验指令是否来自可操作的 Idle 船，读取完整占格和前方最近阻挡。
2. 得到不可变 MoveResult：起点、终点、路径、被阻挡对象或出口。
3. 紧邻阻挡、位移为零时保留原占格，只播放轻撞反馈。
4. 有可移动距离时，为目的占格／必要通道做预约；动画期间不能让其他指令将它当成完全不存在。
5. 完成后一次性更新占格、位置与状态；被阻挡则停在新位置，不退回初始位置。
6. 船尾完全离开逻辑边界后释放棋盘占位，进入航道；到达战区才触发加入舰队和攻击。

原型阶段建议先串行处理棋盘移动，以简单规则验证正确性；航道和战斗表现可并行。若后续确需连续多船同时移动，再启用按路径冲突处理，不能依赖全局静态布尔变量勉强扩展。

**边缘航道：**每个出口关联路径入口，四边经可配置路线进入上方汇入口；路径负责视觉流转，不能改变棋盘方向规则。到达使用唯一 transitId／shipInstanceId 去重，Tween 完成回调重复执行也只加入一次舰队。多个实例同帧抵达要保持稳定顺序，以便连融可复现。

### F4. 舰队、攻击与成长的最小清晰定义

按用户现有文字，建议原型采用下列解释，尚未替用户固化未明确的数值：

| 概念 | 建议职责 |
|---|---|
| 同型叠加 | 每种 typeId 一个战区展示实体，记录本局累计融入数量 |
| 自动攻击 | 船到达并融入后自动创建 1 个 AttackToken，不要求玩家再次点击 |
| 攻击次数 | N 艘船抵达，共产生 N 个基础入场攻击令牌；不是第 N 艘到达便额外发射 N 次 |
| 船型／等级 | 决定该令牌伤害；例如读取 ShipStats(typeId, persistentLevel)，具体公式以后配置 |
| 连融 | 在规则允许的时间窗内连续融入相同船型，提升攻击表现档位 |
| 视觉升级 | 炮弹／拖尾／命中特效变化，与永久伤害等级分开存储 |
| 金币 | Boss 击败并按单局结算契约完成后，由唯一 settlementId 发奖 |

如果“自动攻击”还包括独立周期射击，应新增定时攻击规则，并明确聚合数量如何改变频率或每轮次数；不能与入场令牌无意叠乘。连融是否增加伤害，目前文字只明确升级特效，不自行增加战斗收益。

需在开发前确定的规则决策有：

- “连续同型”是全局相邻入场必须同型，还是每个船型分别计算时间窗；建议先采用前者并用入战时刻排序。
- 广告／暂停／切后台是否冻结连融与攻击时间；建议使用统一可暂停的单局时钟。
- Boss 先死亡时，剩余船是否继续清理；船全出完而 Boss 未死时，是否判负或有明确补救。
- 道具移除是否产生入战攻击；洗牌与翻转如何保证不重叠、不过界及可解。
- 最终胜利要求“Boss 死亡”还是“Boss 死亡且棋盘清空”。

这些是尚未确定的设计边界，不影响本报告完成，也不在本次擅自实现。建议把每关可产生的伤害与 Boss HP 一起校验，防止玩家解谜正确却因为配置不足而永远无法获胜。

### F5. UI、存档与平台边界

- Root Canvas 内先应用安全区，再划分 Battle 20%／Board 60%／Tools 20%；以屏幕比例划分 UI，以关卡尺寸计算棋盘相机或缩放，不让密集关自动压缩道具。
- 战区 HUD 展示 Boss HP、同型唯一舰队图标／实体、待攻击／叠加数量与连融反馈；首次加入、同型融入、攻击命中三个时刻要有清晰区分。
- 点击由独立输入层命中船实例，先排除 UI，支持触控指针；不直接复制仅依赖 OnMouseDown 和无指针 ID 的 UI 排除逻辑。
- 进度存档独立于关卡 Scene Build Index，包含 schemaVersion、关卡解锁、船等级、金币、道具和已处理结算 ID；断点恢复范围另定，避免把动画句柄存入存档。
- 广告服务返回 Completed／Cancelled／Unavailable／Failed 等明确结果，由奖励服务发放；Null／本地模拟实现仅供开发，不在生产自动发放真实广告奖励。
- Google Play、TapTap 是发行渠道，Android、iOS 是平台维度，配置应拆开。当前资产未提供本游戏的 TapTap 专用接入能力；是否需要渠道登录／支付等，由实际发行需求确定，不预装无关 SDK。
